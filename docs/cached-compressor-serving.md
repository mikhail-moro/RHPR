# Future cached-compressor serving evaluation

Caching changes the cost question: the present uncached forward and training measurements do not establish online serving efficiency. Both Cross Attention (CA) and QSSM can cache the four output summaries when their history boundary and query support stay fixed. Compare them under the same refresh and raw-tail policy; a possible QSSM streaming-state advantage would require a separate implementation and test, especially because current queries and relative memory features change when the boundary moves.

## Exact causal contract

Number events from zero and predict item `L[t]` using only `L[:t]`. Fresh inference uses `b=t-128`, `H=L[:b]`, `Q=H[-128:]`, `R=L[b:t]`. Initialize or refresh a cache at `t0`, storing summaries of `H0=L[:b0]`, where `b0=t0-128`. Subsequent cache age is `a=t-t0` observed events; no target or future event may participate in a refresh. For event-count refresh interval `r`, refresh just before prediction when `a=r`; then reset age to zero. Test `r in {1,8,32,128}`. Interval one must reproduce the uncached fresh path, including ranks, before larger intervals are trusted.

Store the **compressor output before SASRec positional embeddings, input normalization, dropout and encoder**, plus its masks, global source endpoint `b0-1`, covered history boundary, query-support range, model/checkpoint/config/dtype and item-vocabulary versions. Bind each entry to the user and causal event-stream version, with refresh event index/time; invalidate on incompatible model/data revisions. The compressor's internal query/memory positional features remain those computed at refresh. At prediction time, reapply SASRec PE using the current global event position: cached summaries have recency `t-b0 = 128+a`, whereas raw tokens retain their actual source positions. Reusing summary recency 128 at every prediction would hide staleness and change the positional contract. The current table clamps recency to its maximum: record any clamp count and avoid silently conflating very old ages. Hash and audit actual Q/R supports and the maximum consumed event index.

## Choose the raw-tail policy explicitly

- **Growing tail, recommended primary quality control:** reuse the cached summaries and feed `L[b0:t]`, initially 128 tokens and then `128+a`. Every past event after the summary boundary remains represented. Predictor input is `4+128+a`, so latency/attention cost must be measured at the actual age. This is a valid causal continuation of the initial cache, but longer raw tails are outside the current 128-token training support and should be labeled as such.
- **Rolling R128, optional fixed-cost serving policy:** feed `L[t-128:t]`. At age `a`, events `L[b0:t-128]` are in neither the frozen summaries nor the raw tail. The resulting quality change combines summary/query staleness with an explicit coverage gap. Log its event count; do not describe this as pure cache staleness. Compare this same policy for CA and QSSM. An incremental writeback scheme that closes the gap is a further method, not a free property of the current models.

Use fresh summaries + R128 as the production-quality reference at exactly the same prediction anchors. For the growing-tail policy, add a fresh re-encoding of the *same frozen boundary* and same growing raw tail as an implementation identity check; its output should equal the cached path. It cannot measure the quality benefit of shifting the compression boundary. Report policy-specific comparisons so increased raw context or missing events are visible.

## Sampling and quality

Build dense causal held-out event schedules for each user; the current sparse daily anchors alone do not supply all cache ages or an event-by-event update trace. Keep the cohort, catalogue, target eligibility and OOV-zero policy fixed. Use deterministic user-bound refresh phases, balanced across age and calendar position, and pair fresh/stale predictions on identical anchors. Preserve a chronological warm-up before measured targets. Prevent age from merely indexing later holdout dates, and require adequate users/targets in each age bin. Any difference from the current daily-anchor support must be reported explicitly.

Plot macro-user NDCG@10 and @100, and paired stale-minus-fresh changes against event age (also elapsed wall-clock time), separately by policy/interval/model. Bootstrap users rather than treating their repeated targets as independent. Do not assume the first prediction is best or deterioration monotonic. Exploratory low-popularity-user and target-frequency subgroups may be reported separately; target PopBias and catalogue coverage require their own measurements and do not follow from the existing user-history subgroup.

## Serving measurements

Run identical user/anchor microbatches 1/8/32 on the same hardware, separating compressor refresh, cache lookup/transfer, SASRec and full-catalog scoring. Report both warmed cache hits and refresh misses, request p50/p95 under an explicitly specified hit/miss mix and refresh scheduling policy, and amortized mean cost `(all refresh + lookup/transfer + predictor + scoring time)/predictions`. Include initial cache construction or report its exclusion, total GPU/CPU peak and resident memory, cache bytes/user, transfer bytes, and actual sequence lengths; refresh summaries are only four vectors but raw-tail buffers, model weights and any SSM state also count. Synchronize CUDA measurement and keep batching/warm-up rules identical. A large ranking cost can dominate both methods, so retain component as well as end-to-end timings. Asynchronous refresh additionally needs a queue/capacity test and a rule for serving during refresh; it should not be simulated by silently removing refresh time.

This is a later evaluation specification only. The currently authorized compressor HPO should not be delayed or extended by implementing it now.
